# 项目开发规则

## 实施与验证

- 遵守 KISS 和“如无必要，勿增实体”，不为假设的未来需求预建框架或抽象。
- 选型顺序：Flutter SDK／官方包 → 成熟第三方组件 → 有明确缺口时的最小自定义适配。新增功能与已有实现核查均遵循此顺序，现成能力满足需求即停止，不以已有代码或测试通过代替选型依据。
- 第三方仅在当前需求确有必要时引入，核对多端支持、平台依赖、Flutter 升级维护及接入／替换成本；“成熟”或当前编译通过不等于可靠适配。优先公开 API，不为尚未要求的平台预建兼容层。
- mihomo／依赖变更按[许可处理依据与升级复核](../../docs/dependency-licenses.md)核对实际解析图、固定许可证据和最终产物，同步锁文件及随包通知；不因间接依赖删除必要版本要求，也不将旧结论视为新版本的自动许可保证。
- 自定义适配说明具体缺口，源码限于必要范围，不增加无需求的兼容分支、备用路径或框架。标准组件组合与项目业务逻辑不等于重复造轮子，不为替换少量简单代码引入依赖；已有实现替换需比较行为兼容、整体复杂度和迁移代价，核查不自动授权全面重构。
- 按当前用户任务裁剪范围，不把“最终重要”当成“现在优先”，不以全面工程清单、局部修复或可开展的工作替代产品主线。
- 改动小而可验证，不顺带重构、升级或扩大功能，保留用户无关改动。
- 沿用已有风格，正确处理错误、资源释放与生命周期。
- 默认在当前分支工作；未经要求不创建或切换分支，不参考或迁移 legacy 分支。
- 不擅自安装工具，或调整工具链版本、平台插件与发布配置。
- CodeGraph 工具可用时，理解或定位代码优先使用它；本项目索引缺失或过期时，允许按需创建或更新本地索引，不将索引和日志纳入 Git。查询结果不足时核对实际源码；工具不可用则正常查阅文件，不自行安装工具。
- 文档改动检查链接、格式和范围；应用改动执行相关分析、测试和构建。后台、网络、权限与生命周期行为需要相应设备验证，范围随本次改动裁剪。
- 如实报告失败和未验证项，不把编译成功当作功能正确。修复 BUG 时补回归测试；不适合自动化则记录复现与检查方法。
- UI 改动必须遵守[布局跳动禁令](../../docs/product-requirements.md#通用设计原则)。检查等待、成功、失败、重试、选中、禁用、异步刷新、上下文失效及恢复的中间帧，比较位置、尺寸与阅读锚点，并覆盖相关长文本、窄屏与大字号。发现潜在跳动路径必须修复，不以正常截图、无溢出、最终帧或现有测试通过替代验收；复杂浮层与状态切换补相应设备验证，未验证的范围明确列出。

## 提交与文档

- 一个已批准计划是完整执行单元。分阶段只用于组织实施与验证，不是可自行停止的边界；必须连续推进全部阶段，使约定范围完整、已明确的应用自身问题解决、相关验证与文档及差异审查完成，全部成果达到可提交状态后才交付用户验收。不要求先补齐所有未来平台或发布检查。
- 执行过程中不暂存、不创建 commit，不按阶段提交，不在阶段间询问是否提交或要求用户再次催促继续。计划实施批准不是 Git 提交授权；全部成果交付后，由用户评估满意度并另行决定是否及如何提交。用户要求返工时继续修正并重验，达到可提交状态不等于用户已经满意或正式验收通过。
- 禁止以进度汇报、局部测试通过、截图检查、清理测试环境或列出剩余工作结束未完成的计划；写明“尚未完成”不能合理化无阻塞的主动停止。只有用户明确暂停／改向、权限拒绝，或无法在已授权范围内解决的真实阻塞才可中断相应工作；说明证据、受阻范围与恢复条件，完成不受影响的已授权部分，不把中断称为完成，不绕过权限。
- 最后获得提交授权后，只提交已明确的任务范围；授权不自动延伸到后续任务，不推送或发布。
- 提交使用英文 `type(scope): subject`，一个提交一个目的，标题简短且不以句号结尾。
- AI 协助统一在提交正文标注 `Assisted by AI`，不使用具体厂商或模型署名，不猜测邮箱；保留正常 Git 作者信息。
- 文档使用中文，命令、路径、标识符和工具输出保留原文。
- 按职责放置内容，不复制已有说明，不写 AI 自述或操作流水；任务进度留在任务与汇报中，不写进 README。
